# 国产算力与智能芯片上市公司财报问答知识库构建
## ——基于向量检索与 BM25 的混合 RAG

> 课程作业 A 最终实验报告。所有数据规模、运行耗时和检索覆盖率均来自 GitHub Actions 的真实运行记录；人工结论依据项目财报语料和召回证据复核。

## 一、研究背景

上市公司半年度报告同时包含管理层讨论、主营业务、核心技术、研发活动、风险因素以及大量财务报表和附注。对于国产算力与智能芯片企业而言，不同公司在 AI 训练与推理芯片、CPU、GPU、端侧 SoC、芯片 IP、FPGA 等技术方向上具有明显差异，仅依靠关键词搜索难以稳定回答同义表达和技术路线问题；而仅依靠向量检索，又可能在公司名称、芯片型号、会计科目、报告期等需要精确匹配的信息上产生误召回。

因此，本项目选取 10 家国产算力与智能芯片相关上市公司，以统一报告期的 2026 年半年度报告为知识来源，构建“BM25 + 向量检索”的混合财报问答知识库。系统要求所有回答尽量回链至具体公司、报告期、章节和页码，并通过 10 道测试题观察单公司问题、双公司比较问题和跨公司全景问题的差异。

## 二、样本与数据范围

样本公司包括：寒武纪、海光信息、龙芯中科、景嘉微、芯原股份、瑞芯微、全志科技、北京君正、国科微、复旦微电。

统一报告期为 2026 年半年度报告。数据源优先使用上海证券交易所、深圳证券交易所公告 PDF；当公开检索稳定返回巨潮资讯的报告全文 PDF 时，仓库会如实标记为 CNINFO 来源，不把巨潮链接伪装成交易所直链。

10 份报告全文链接均已通过自动 source-check 验证。全量语料共 1,730 页；解析后形成 5,073 个知识块，其中正文块 2,367 个、表格块 2,706 个。各公司块数分别为：寒武纪 461、海光信息 426、龙芯中科 482、景嘉微 445、芯原股份 727、瑞芯微 390、全志科技 643、北京君正 560、国科微 495、复旦微电 444。

## 三、系统设计

### 1. 文档解析

PDF 解析分为正文与表格两条路径。正文按页提取并识别当前章节；表格尽量保留原始行列关系。每页记录包含公司名称、证券代码、报告期、报告标题、页码、章节、正文、表格以及原始文件名。

### 2. 切块与元数据

正文目标块长度约 900 个汉字，相邻块保留约 120 个字符重叠，并优先在句号、问号、感叹号和分号后切分。表格作为独立块保存，避免将表头和关键数值完全分离。

每个块至少保留：

- 公司名称
- 证券代码
- 报告期
- 章节
- 页码
- 内容类型（正文 / 表格）
- chunk_id
- 原始文件名

这样做的目的，是避免财报问答中出现“数字本身正确，但公司、期间或口径错误”的情况。

### 3. BM25 检索

BM25 使用 jieba 分词。其优势主要体现在公司名称、证券代码、产品型号、专业术语以及会计科目等需要字面匹配的信息。

### 4. 向量检索

正式实验使用 `BAAI/bge-small-zh-v1.5`，将“公司名 + 章节 + 页码 + 正文/表格内容”共同编码，生成 512 维归一化向量。其主要作用是召回同义表达、业务场景和技术路线等语义相近内容。

项目曾先尝试 `Qwen/Qwen3-Embedding-0.6B`。在 GitHub Actions 普通 CPU runner 上，batch_size=4 时前 7 个 batch 平均约 254 秒/批，1,269 批按线性估算约需 89.7 小时，不具备课程作业的可复现性，因此正式实验改用轻量 BGE-small。该调整只改变 embedding 模型，不改变 BM25、向量检索、RRF、题目集和评价口径。

### 5. 混合召回

BM25 与向量检索默认分别召回 top-10，再使用 Reciprocal Rank Fusion（RRF）按排名进行融合，最终保留 top-8 作为回答证据。当前版本故意保持结构简单，以便清楚观察基础混合 RAG 在跨公司全景问题上的能力边界。

### 6. 回答与溯源

回答模型只能依据检索出的证据作答。证据不足时应明确说明“当前检索证据不足，无法确认”，不得自行补充未被召回的财务数字。回答页面同时显示证据块的公司、章节、页码、检索路线和 RRF 分数。

## 四、测试题设计

共设置 10 道测试题：

- Q1-Q6：单公司数字、产品、技术路线和商业模式问题；
- Q7：两家公司比较问题；
- Q8：多公司研发投入变化问题；
- Q9-Q10：跨公司全景题。

其中 Q9、Q10 用于重点观察固定 top-k 是否会遗漏部分公司，以及普通碎块检索能否覆盖“十家公司之间的共同技术路线、风险与应对措施”。

完整测试题见 `evaluation/questions.json`。

## 五、评价方法

本项目不只判断最终答案“看起来是否合理”，还记录检索层证据：

1. 召回了哪些 chunk；
2. 覆盖了哪些公司；
3. 证据是否足以回答问题；
4. 最终回答是否正确；
5. 错误属于哪一类。

计划重点分析以下错误：

- 公司召回错误；
- 本期 / 上期混淆；
- 合并 / 母公司口径混淆；
- 表头与数值被切开；
- 专有名词同义表达导致 BM25 漏召回；
- 向量检索未精确命中型号、公司名或科目；
- 跨公司题 top-k 只覆盖少数公司；
- 证据不足但生成模型仍试图补全答案。

## 六、实验结果

正式 `retrieval-build` 在 GitHub Actions 的 `ubuntu-latest` CPU runner 上成功完成。5,073 个知识块全部建立 512 维向量；BM25 与 BGE-small 索引构建约 5 分 52 秒，10 道测试题检索约 10 秒，整个 workflow 约 7 分 11 秒。

| 题号 | BM25公司覆盖 | 向量公司覆盖 | 混合公司覆盖 | 人工复核 |
|---|---:|---:|---:|---|
| Q1 | 0% | 100% | 100% | 部分充分：命中寒武纪，但存在合并/母公司口径风险 |
| Q2 | 100% | 100% | 100% | 充分 |
| Q3 | 100% | 100% | 100% | 充分 |
| Q4 | 100% | 100% | 100% | 充分 |
| Q5 | 100% | 100% | 100% | 充分 |
| Q6 | 100% | 100% | 100% | 充分 |
| Q7 | 50% | 50% | 50% | 不充分：缺少全志科技 |
| Q8 | 60% | 80% | 50% | 不充分：无法保证十家公司穷尽性 |
| Q9 | 40% | 70% | 60% | 不充分：混合检索仅覆盖 6/10 家 |
| Q10 | 70% | 60% | 50% | 不充分：仅覆盖 5/10 家且存在弱相关噪声 |

10 道题平均公司覆盖率为：BM25 72%、向量检索 86%、RRF 混合检索 81%。混合检索并未在所有问题上超过单一路径，原因是固定 Top-8 容易被少数高相关公司的多个块占满，使跨公司问题出现“相关但不全”的情况。

人工复核发现，Q2-Q6 的单公司产品、技术和商业模式问题均有充分证据。Q1 虽然命中寒武纪，却没有把第 7 页合并口径“主要会计数据”表稳定放入混合 Top-8，同时召回了母公司利润表，因此数字题需要额外控制公司、期间、合并/母公司、单位和科目。Q7-Q10 则说明比较题和全景题应采用分公司检索与覆盖率检查，而不是只对全部语料执行一次 Top-K。

本次 CI 未配置生成模型 API，因此 `evaluation/results.csv` 中的 `answer_correct` 表示基于人工参考答案和召回证据进行的“可回答性/证据充分性”复核，不是自动 LLM 评分。完整逐题记录见 `evaluation/retrieval_runs.csv`、`evaluation/results.csv` 和 `evaluation/reference_answers.md`。

## 七、结论

第一，单公司事实和语义问答适合 BM25 + 轻量向量混合 RAG。Q2-Q6 均能稳定找到足够证据，说明在公司范围明确时，关键词精确匹配与语义检索可以互补。

第二，财务数字题需要在语义检索之外增加结构化口径约束。Q1 暴露了合并报表与母公司报表可能同时进入候选的问题，仅凭相似度无法保证财务口径正确。

第三，普通固定 Top-K RAG 不适合直接承担跨公司全景任务。Q7-Q10 的公司覆盖明显下降，表明后续改进应优先加入公司识别、问题拆分、按公司独立检索、证据覆盖检查和 Agentic RAG 式汇总，而不是单纯更换更大的 embedding 模型。

因此，本项目最终不仅完成了财报知识库和混合检索系统，也通过真实实验识别出了普通 RAG 的适用边界：它擅长“在明确对象中找到相关证据”，但要完成“对多个对象完整覆盖并保持财务口径一致”，还需要更强的检索规划与证据组织。
